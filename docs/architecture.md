# Architecture and domain roadmap

## Boundaries

- `apps/web` owns the authenticated business dashboard, Document Vault, and a separate external counterparty review layout. Live invitation links support customer responses; the `/review/demo` shell remains illustrative.
- `services/api` is a FastAPI modular monolith. API routes use domain services for persistence, while dependencies enforce authentication, CSRF protection, membership and permissions. SQLAlchemy owns persistence; Alembic versions schema changes.
- Customer and transaction records are live only after business sign-in. A transaction is not itself an agreement; initial amounts marked paid are business reports, not verified payment events. Counterparties never receive dashboard accounts.

## Domain ownership and lifecycle

A Business owns memberships, counterparties, transactions, agreements, obligations, documents, and audit events. A User may belong to multiple businesses through BusinessMembership; each request must carry an authorised business context and permissions. A Counterparty is a business-managed record, never a user account. TransactionItem belongs to a Transaction, while Agreement and AgreementVersion describe proposed or accepted terms linked to that transaction. The server, not the browser, must enforce draft → invited → confirmed or correction/rejection transitions. Sending or opening an invitation does not confirm terms.

AgreementInvitation and ConfirmationChallenge bind a counterparty, transaction, and immutable agreement version. ConfirmationEvent records the explicit response and exact version. Material changes create a new version and invalidate stale challenges. Payment events and Obligation balances remain distinct from agreement state; a reported payment must be distinguishable from one independently acknowledged. NegotiationProposal and Dispute preserve their histories without rewriting confirmed terms. DocumentVersion records immutable content metadata and integrity information; object bytes live behind a private local or S3-compatible storage adapter.

## Tradeoffs

The Phase 1 migration remains an empty baseline. Phase 2 adds users, businesses, memberships, server sessions, counterparties and transactions. Phase 3 adds versioned credit agreements, hashed invitation tokens, hashed short-lived challenges, confirmation events and audit events. The owner creates staff accounts with explicit permissions; staff never inherit settings or agreement access. All business record reads and writes are scoped by authenticated business membership. UUID identifiers prevent casual enumeration, while membership checks provide the actual boundary. A reported initial paid amount is stored on the transaction; payment history is deferred until Phase 5. SQLite enables a simple local workflow; PostgreSQL integration and concurrency tests will be necessary before deployment. No service worker is installed yet because authenticated offline caching needs an explicit retention, conflict, and access design.

The initial agreement lifecycle is `draft → invited → confirmed`, `invited → correction_requested → draft`, or `invited → rejected → draft`. Every edit inserts a new immutable version and revokes outstanding invitations. Acceptance records the exact version and digest after explicit action and a single-use code. The local development code is displayed to the link holder, so the system records `identity_verified: false`. Corrections and rejections are also marked as responses from an invitation link only. The invitation token sits in a URL fragment; the browser sends it in a header to avoid placing it in normal server access logs. After acceptance, the same link can read the confirmed version until its seven-day expiry; it cannot accept again.

The credit-sale template snapshots the saved transaction's business, counterparty, item description, UGX amounts and deadline. The server keeps this core block fixed while business users revise the proposed terms. This prevents the agreement's displayed financial summary from diverging from the transaction. Correcting a core transaction fact currently requires a new transaction record; linked supersession and amendments need a later design.

Phase 4 stores document metadata in the business database and bytes outside it. Owner and staff document permissions are separate from agreement and transaction permissions. Uploads are checked for PDF, PNG, or JPEG signatures and limited to 10 MB. Each file version has a distinct private object key and SHA-256 digest. The API verifies its digest before serving it, and records explicit downloads. A confirmed agreement is copied into the Vault as immutable UTF-8 text during acceptance; the acceptance transaction fails if preservation fails. An idempotent route archives older confirmed agreements. The Vault does not expose direct bucket URLs. Database and object storage must be backed up together; object cleanup after some failure cases may need an orphan sweep.

## Next slice

Phase 5 adds business-recorded payment entries, partial balances, deadlines, proposals, disputes, and append-only activity. A disputed payment is excluded from the working balance until a business user acknowledges it. Accepted extension, instalment, and revised-obligation proposals can set a working deadline; the original transaction deadline and confirmed agreement remain unchanged. Settlement amounts and proposal responses are records only and do not write down debt. These responses are not independently verified or customer-signed. Staff need an explicit obligation-management permission to write them. The Phase 5 migration expands the schema without modifying prior records; rollback drops the new tables and their data.

Phase 6 adds explicit IndexedDB transaction drafts, a stable API request UUID for idempotent retries, optional browser speech suggestions, a token-bound proposal response path, and opt-in SMTP or HTTPS SMS-link delivery. Offline drafts require the authenticated page to remain open while disconnected; a reload needs online sign-in. The proposal link follows the agreement's seven-day token and development-code boundary. Link-only correction and decline responses are recorded without identity verification; acceptance remains unavailable when development verification is off. Original transaction and agreement terms remain immutable. USSD and further legal-template decisions are described in [Phase 6 integration notes](phase6-integrations.md). Before production, add independently delivered verification, provider receipts and abuse controls, PostgreSQL concurrency tests, and legal review of electronic agreements in Uganda.
